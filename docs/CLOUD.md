# 本地研究与Railway执行

版本0.15.3。只支持模拟交易，无杠杆、无真实券商执行。从0.14.0升级的顺序、设置和验收见 [升级到 0.15.0](UPGRADE_0.15.md)、[升级到 0.15.1](UPGRADE_0.15.1.md)、[升级到 0.15.2](UPGRADE_0.15.2.md) 和 [升级到 0.15.3](UPGRADE_0.15.3.md)。

本地运行资料收集、研究、组合决策和每日48小时复盘；云端运行报价更新、价格条件检查、风险控制、模拟委托及成交。云端账本是唯一主账本，本地通过签名API取得只读副本。研究输入、完整原文、大模型登录和私钥留在本地。

## 时间与失联

- 研究仍每6小时、新闻每30分钟、组合每小时复核。日线、资料、事项核验、财务底稿、已采纳研究规则和版本号都未变化时，研究可在上次模型研究后的 `research_reuse_hours` 小时内沿用其结论，不调用模型；沿用时照常生成新版本的计划（有效期重新计算），参与组合决策和发布。休眠后合并到最近一次研究；断网恢复后补跑最新研究与最近复盘，历史交易时点不补单。
- 分离模式下组合授权最长12小时；底层研究、公告、行情和外汇可能更早失效。云端每小时确定性复核不调用模型，也不延长底层研究期限。
- 研究心跳是签名策略里的实际完成时间，必须经云端校验接收。进程心跳、拉取账本、重传旧包、复盘上传都不能刷新它。研究确认保持原策略也可发布新的复核版本。
- 12小时无有效研究心跳：停止新买入、撤销OPEN/PARTIAL买单；UNKNOWN保留待核对。继续价格和风险检查、止损及必要退出。持仓不会只因研究过期强制全部卖出。
- 新研究导致旧依据失效时先发送签名失效通知，暂停旧组合授权；随后新的完整组合版本恢复可执行授权。0.15.0 起失效通知只列来源计划有变化的候选（`keys`），云端只暂停依赖这些候选的授权，其他候选的授权继续有效；所有候选的来源都没有变化时不发送失效通知。

## API与数据

POST `/api/sync/{bootstrap,strategy,ledger,reviews,invalidate,activate}` 要求本地Ed25519签名，绑定路径、时间、随机序号和压缩正文摘要。云端只有公钥，网页Admin/Guest均无策略写权限。请求时间误差不得超过5分钟；成功请求随机序号不得重复。

策略序号持久单调递增。旧包、内容冲突和过期包拒绝；完全相同包重试仅返回原回执，不续心跳。新版本、源计划、执行资格、目标仓位和UI研究摘要同事务接收；发布时账本已变化则拒绝，安排本地重新判断。正常报价/净值标记变化不会使每轮分析失效；现金、持仓、挂单与风控锁定变化会。

原A股价格和事项规则、动态公司/历史准入以及海外资产规则保留；云端执行时继续检查新公告、报价、市场时段、有效期、现金、仓位、T+1及无杠杆规则。组合层不能放宽13的硬风控。

策略包附带当前研究摘要、新闻与复盘展示数据；不传完整本地资料库或模型登录。首页每只资产显示“上一次交易策略更新时间”；这个时间不随报价或单纯重传变化。完整输入/输出和回执保存在本地 `workflow/cloud-sync/`；0.15.0 起发布包发送成功后，数据库里只保留哈希标记，目录里只写记录哈希和大小的 `manifest.json`，不再保留 5–6MB 的完整副本。

### 增量同步（0.15.0）

- 云端在 `/health` 和每次账本响应中用 `features` 公布支持的能力：`ledger_v2`（增量账本）、`targeted_invalidation`（按候选失效）、`display_delta`（展示数据按分区发送）。本地只在云端公布后使用对应能力，所以新云端兼容旧本地，反过来不成立。
- 增量账本：云端用触发器把可变表（账户、委托、持仓批次、风控状态等）的新增和修改记入 `ledger_changes`；本地带变更游标拉取，只收到游标之后变化的行，以及满足外键所需的关联行。游标早于云端保留的最早记录（变更日志保留 7 天）时，自动改为完整传一次可变表。
- 展示数据：本地按分区计算哈希，只发送云端没有的分区；云端合并后返回实际持有的分区哈希，本地据此决定下次发送什么。报价、最近检查、未成交委托和“上一次交易策略更新时间”由云端按自己的账本和已接收的策略计算，不随分区发送；0.15.1 之前后者被一并发送，导致每次发布都重发全部股票分区。
- `/health` 只返回 `ok`、`version`、`role`、`features`、`code`（代码指纹）和 `calendar`（已录入的交易日历版本），不含任何账户数据。`code` 与本地 `./agent doctor` 输出的 `build.code` 相同，表示两端代码一致。

## 部署

1. 使用私有GitHub仓库，只提交源码、Dockerfile和无密钥配置。`.gitignore`排除本地config.json、数据、认证、私钥和部署工具目录。
2. Railway自动检测Dockerfile，使用单副本、持续运行；挂载持久卷 `/data`。SQLite、回放防护、风险锁定和小时备份都在持久卷；不要启用Serverless休眠。在服务设置保存公开HTTPS域名、健康检查 `/health` 和超时180秒。新服务不依赖已停止接受新用户的旧railway.toml配置方式。
3. 云端变量：`THESISTRADE_ROLE=cloud`、`THESISTRADE_DATA_DIR=/data`、`THESISTRADE_PUBLIC_ORIGIN=https://实际域名`、`THESISTRADE_SYNC_KEY_ID`、`THESISTRADE_SYNC_PUBLIC_KEY`。`PORT`由Railway注入。云端没有大模型登录与私钥。
4. 本地配置 `deployment_role=research`、`sync_cloud_url=https://实际域名`、`sync_key_file=私钥JSON的绝对路径`。通过 `python -m ashare.cloud_cli --config 本地配置 keys` 创建文件，权限0600；仅把输出公钥信息配置到云端。
5. 备份并停止旧的本地交易服务，安装新代码与research角色配置。运行 `cloud_cli ... bootstrap` 一次迁移模拟账本及登录密码哈希（不迁移登录会话），云端此时仍禁止交易。重复初始化被拒绝。
6. 启动本地research服务，拉回账本后生成一轮正式组合决策并签名上传。核对账本、策略、HTTPS登录和云端行情，然后 `cloud_cli ... activate` 启用云端执行。确认本地健康接口为research、云端为cloud。
7. 验收云端分钟任务、断联和重复请求保护，保存前后备份及部署标识。后续GitHub推送自动重新部署，持久卷和风险锁定保留。
8. 版本升级固定先云端、后本地：合并到 `main` 后等 Railway 部署完成，确认 `/health` 的 `version`、`features` 和 `code`，再更新本地代码并重启本地服务。

恢复必须保持单一执行端。不得在云端已启用时把本地改回standalone；需要恢复本地执行时先明确停用云端、取回最新账本并核对未完成委托。

官方部署依据：[Railway持久卷与服务](https://docs.railway.com/services)、[健康检查与PORT](https://docs.railway.com/deployments/healthchecks)。挂载持久卷的重新部署会有短暂停机；恢复后不补执行错过的交易时点。

## 验证

首次检出先将 `config.example.json` 复制为本地 `config.json`（不得提交私钥配置）。Python3.12环境安装pyproject.toml中依赖后：

```
python -m unittest discover -s tests
node tests/test_ui.mjs
```

迁移校验必须使用独立数据目录。测试生成的持仓、策略和账号不得导入正式环境。
