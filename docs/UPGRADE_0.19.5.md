# 0.19.5：审批回执与显式规则替代

批准人姓名不再构成生产修改权限。提案批准、采纳、退役，以及撤回已批准决定、改标用户已拒绝的提案，现在必须使用已登录管理员确认的具体动作回执。STRATEGY设置通过同一机制；运行类设置保留原权限。

## 使用方式

先整理完整提案并标为READY。申请时冻结提案版本、原状态、目标动作、理由和替代明细，经现有通知通路送达管理员页面；页面确认仅生成回执，不自动采纳或改设置。代理随后核对回执并实施。

```bash
./agent proposals request <提案编号> --to APPROVED --replace-none --note "确认此版本方案"
./agent approvals list
./agent approvals show <AR编号>
./agent proposals decide <提案编号> --to APPROVED --replace-none --approval <AR编号> --note "确认此版本方案"
```

采纳需为ADOPTED动作另行申请与消费，不能借用APPROVED回执。若替代已有规则，将`--replace-none`换为明确的`--replaces G-旧规则编号`，多条可重复传入；批准和采纳的清单须一致。不列入清单的互补规则继续生效。**替代会撤下所列旧规则整条**，包括其完整适用范围，不按新旧范围交集切割旧文本。

```bash
./agent config request paper_entry_band_bps=100 --reason "已审阅提案中的具体变更"
# 管理员确认该次精确差异后，使用返回的AR编号：
./agent config set paper_entry_band_bps=100 --reason "已审阅提案中的具体变更" --approval <AR编号>
```

以上数值仅演示命令，不在本次部署中执行。网页策略设置保存同样只登记待确认请求，明确告知尚未生效；运行类保存保持原行为。旧`--approved-by`参数不再提供授权。

## 一致性与恢复

请求有效期24小时，绑定完整实质内容版本、具体对象、动作和替代范围。确认后内容、原状态或待替代规则改变，原回执失效；旧APPROVED记录没有新版回执时，不自动获得新权限。共享admin账号提供已认证账号来源，不等同于实名证明，也不能隔离具有同一系统账号任意写权限的程序。

研究规则的新采纳、旧规则退役、所属提案历史和回执消费在同一SQLite事务中完成，失败一起回滚。采纳后按原规则改变build，历史有效区间保留。

配置文件与数据库不共享事务，因此配置实施采用文件锁、已提交的操作意图、回执预留、原子文件替换和日志去重。服务启动及后续配置操作会恢复中断的已授权操作，也可执行`./agent config recover`。尚未发布且能证明没有发布痕迹的过时意图会终止并保留记录，需重新申请；已发布则仅补齐日志和消费。第三方改变文件造成状态不明时停止恢复，绝不覆盖。

云端先升级，本机再升级。旧云端未声明`approval_receipts_v1`时不发送审批请求；普通通知保持兼容。过期审批退出当前待办但保留历史，有效请求优先同步，历史决定仍可补同步。

本次部署不批准或采纳任何生产提案，不修改策略设置、研究提示词、固定模型、交易或评分逻辑。完整代码冻结机制保持原样，已授权实验按实现版本分别留存，不拼接样本。
