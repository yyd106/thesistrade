# 升级到 0.15.1

0.15.1 是 0.15.0 上线后的补丁（2026-09-26）：新增程序生成的运行日报和手动登记工程问题的命令，并修正上线时发现的两处问题。交易规则、研究提示词、模型和策略类设置都不变；硬性风控、本金、提取档位和市场范围不变。

## 改了什么

**运行日报（新增）**

本机（研究端）每天 23:50 把当天各环节做了什么汇总成一页，供用户和监督检查使用。日报由程序从数据库和运行记录直接统计，不调用模型、不写数据库、不改任何设置。

- 位置：`ashare-data/workflow/digests/<日期>.md`，同名 `.json` 是同一内容的结构化版本。
- 内容依次为：需要关注、抓取、研究（每只自选股一行：研究结论、计划、主要限制、结论来自新研究还是沿用、较前一日是否变化）、组合策略（决策、发布、最长发布间隔、较前一日的变化）、云端执行（成交、净值、持仓、风控）、复盘（程序检查结果、发现去向）、调整与治理（设置修改、提案、研究规则、工程问题、桌面 agent 笔记）、任务运行（各类任务的结果和最长耗时）。
- 云端执行一节读的是本机每 60 秒从云端同步的账本副本。
- 某一节统计出错时，该节写明“本节生成失败”和错误原因，其余各节照常生成；不会用空白冒充“当天没有发生”。

“需要关注”一节由固定规则产生。规则只指出该去看哪里，本身不是结论：

| 规则 | 触发条件 |
|---|---|
| 抓取失败率 | 当天采集尝试不少于 20 次，且失败占 20% 以上；另列其中网络类错误的次数 |
| 资料研究任务未完成 | 资料研究、资料采集或研究任务以失败、推迟或中断结束 |
| 研究模型调用失败 | 研究生成失败不少于 3 次，或模型研究中失败占 30% 以上 |
| 研究实际使用了非固定模型 | 当天计划记录的实际模型与 `model_name` 不一致 |
| 组合策略发布最长间隔 | 相邻两次成功发布的最长间隔不少于 3 小时。首段从前一天最后一次发布算起，末段算到日终（当天的日报算到生成时刻）。云端 12 小时收不到新策略就停止新买入 |
| 当天没有成功发布到云端的组合策略 | 当天没有一次发布被云端接收 |
| 当天复盘未成功 | 复盘不是“成功”或“无需分析”；当天的日报只在复盘时间所在的小时过后才检查 |
| 复盘程序检查未通过 | 复盘的一致性检查有未通过项，逐项列名 |
| 风控已触发暂停 | 组合风控状态为暂停 |
| 策略类设置被修改 | 设置修改记录里有策略类的修改，逐项列名 |
| 新增工程问题 | 当天首次登记的工程问题 |
| 服务曾中断或断网 | 有恢复连接后补跑的任务 |

区间汇总：`./agent digest --since <开始日期> [--until <结束日期>]`（最长 62 天）写出 `workflow/digests/rollup-<开始>_<结束>.md`，包含逐日概况表、按日期排列的需要关注事项、区间内的全部调整与治理事件和期末状态。汇总逐日从数据库重新统计，不依赖每天的日报文件是否已经生成。

两处时间边界：

- 23:50 生成的当天日报不含 23:50 之后发生的事；次日重新生成或做区间汇总时会补上。
- 电脑在 23:50 处于睡眠时，醒来后补生成，日期仍按原来那一天。

生成时间由运行类设置 `digest_time` 控制（默认 23:50）。手动生成某一天：`./agent digest --date 2026-09-25`。

**手动登记工程问题（新增）**

0.15.0 的工程问题只能由复盘自动登记，桌面 agent 在待办或日报里发现的程序缺陷没有登记入口。现在可以用：

```sh
./agent issues new --key OTHER_DATA --title "巨潮公告目录连续两天为空" --detail "现象与依据" --evidence workflow/digests/2026-09-27.md
```

- `--key` 只能用复盘分流所用的问题类型（`OTHER_DATA`、`OTHER_SYSTEM`、`OTHER_EXECUTION`、`MISSING_DAILY_BARS` 等）；程序检查类问题仍只由复盘登记。
- 同一类型、同一代码、同一标题再次登记时只累加次数；已解决的问题再次登记会重新打开。
- 记录里带 `source:agent`，与复盘登记的问题区分开，并出现在当天日报的“调整与治理”一节。

**展示数据增量的修正**

0.15.0 起，策略发布中的展示数据按分区计算哈希，只发送云端没有的分区。每只股票的分区里带着“上一次交易策略更新时间”，而每个新策略版本都会更新所有资产的这个时间，于是每只股票分区的哈希每次都变，每次发布都重发全部股票分区。云端展示这一时间时本来就按自己收到的策略重新计算，所以 0.15.1 不再把它计入分区。

升级后第一次发布仍会重发一次全部分区：本机记住的是云端按旧算法返回的哈希。之后只发送确实变化的分区。可以在该次发布目录的 `manifest.json` 里看 `display_sections_sent` 核对。

**本机服务重装**

2026-09-25 上线时，`service install` 在停掉旧服务后 12 秒就加载新服务，launchd 仍在等旧进程退出，报 `Bootstrap failed: 5: Input/output error`。现在：

- `service install` 先停旧服务并等它退出，最长 30 秒；30 秒内没退出就报错且不加载新服务，稍后重跑即可。
- 加载遇到 `Input/output error` 时间隔 5 秒重试，最多 3 次。
- `service uninstall` 的返回增加 `stopped`，表示旧进程是否已经退出。

## 兼容性与部署顺序

数据库结构和云端协议都不变，两端可以按任意顺序更新。按惯例仍先云端、后本机：

1. **云端**：合并到 `main`，Railway 自动部署。
2. **本机**：用旧代码停服务，同步新代码，再用新代码安装服务。

代码指纹是 `build_id` 的组成部分，所以升级后 `build_id` 会变：第一轮研究不沿用旧结论，全部自选股重新调用模型研究（与 0.15.0 上线时相同），之后恢复按 `research_reuse_hours` 沿用。

## 本机设置

不需要修改任何设置。要改日报生成时间时用 `./agent config set digest_time=23:30 --reason 理由`（运行类设置，自动留痕）。

- [ ] 云端 `/health` 返回 `version` 0.15.1，`code` 与本机 `./agent doctor` 的 `build.code` 一致。
- [ ] `./agent schedule` 显示 `digest_time`。
- [ ] `./agent digest --date 2026-09-25` 生成 `workflow/digests/2026-09-25.md`。对照当天的实际情况核对需要关注一节：当晚断网（18:00 那轮资料研究拖到 22:19，19:30 复盘失败，16:44 到 22:22 之间没有新的组合发布），当天还修改了 `model_name` 和 `model_reasoning_effort` 两项策略类设置；日报应标出其中对应的项目。
- [ ] 升级后第二次组合发布的 `manifest.json` 中，`display_sections_sent` 只含变化的分区，不再是全部股票。
- [ ] 第二天早上 `workflow/digests/` 下有前一天的日报。

## 回退

在 GitHub 上还原合并提交，Railway 自动部署回 0.15.0；本机同步回 0.15.0 的代码并重装服务。已生成的日报文件留在 `workflow/digests/`，不影响旧版本运行。
